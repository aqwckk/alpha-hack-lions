# Надежность, масштабирование и сопровождение

Цель проектирования: сохранять заявку при сбое и предотвращать повторную обработку. Механизмы ниже присутствуют в коде; нагрузка, длительная работа и сбои реальных провайдеров не верифицированы. Это не гарантия надежности промышленной системы. [Границы проверки](../product/implementation-status.md#границы-верификации).

## 1. Идемпотентность

| Где | Механизм |
|---|---|
| Команды пользователей | заголовок `Idempotency-Key`: строка ключа вставляется в той же транзакции, что и команда; повтор с тем же ключом и телом возвращает сохраненный ответ (`Idempotent-Replayed: true`), с другим телом `422 IDEMPOTENCY_KEY_REUSED`; параллельный дубль ждет на уникальном индексе и получает тот же ответ |
| Задачи воркера | `jobs.idempotency_key` для задач, которые нельзя ставить дважды (`ISSUE_LOAN:{application_id}`, `PREPARE_DOCUMENTS:{application_id}:{option_id}`); задача хранит ожидаемый статус и завершается без действий, если заявка ушла дальше |
| ЭДО | ключ `EDO:{application_id}:{option_id}`: повтор возвращает тот же пакет |
| АБС | ключ `application_id`: повтор задачи или ручной `RETRY_PROCESSING` после сбоя не создают вторую выдачу; в банке уникальны `loans.application_id` и `loans.abs_operation_id` |
| Подпись | ключ `SIGN:{application_id}:{signing_code_id}` в ЭДО, одна подпись на заявку (`signatures.application_id` уникален) |

Миграция `0002` добавляет `integration_requests`. Воркер фиксирует ключ и тело запроса в отдельной завершенной транзакции до вызова ЭДО или АБС. Повтор берет сохраненный запрос; полученный ответ записывается в `response` до локального завершения этапа. Отсутствие ответа в БД означает неизвестный исход, а не доказательство отсутствия внешней операции.

Для ЭДО результат сначала ищется по ключу пакета; новый пакет запрашивается только при подтвержденном отсутствии. Для АБС повторяется запрос с тем же ключом и неизменным телом: симулятор возвращает прежнюю операцию или отклоняет несовпадение тела. Это реализованная сверка в контракте симулятора, а не проверенная интеграция с реальной АБС. Реестр пакетов и операций симулятора находится в памяти и сбрасывается при его перезапуске; durable-запрос банка не гарантирует восстановление потерянного состояния провайдера. Нельзя создавать новый ключ только потому, что предыдущий вызов завершился таймаутом.

Выдача использует график из подписанного пакета. Ответ АБС сверяется с номером договора, первой датой и графиком запроса; график сохраняется в `loans.payment_schedule`. Сохраненное расписание используется при чтении выданного кредита; реальные транши линии и банковское начисление процентов этим не моделируются. Основание: [задачи воркера](../../services/api/app/worker/tasks.py), [клиент интеграций](../../services/api/app/services/integrations.py). Результаты проверок: [audit-fixes.md](../testing/audit-fixes.md).

## 2. Конкурентные изменения

* Оптимистичная блокировка: каждая команда передает `expected_version`, смена статуса выполняется условным `UPDATE ... WHERE id AND status AND version`. 0 обновленных строк: `409 VERSION_CONFLICT` или `409 INVALID_TRANSITION`.
* Гонка "Взять в работу": проходит первая транзакция, второй андеррайтер получает `409 ALREADY_TAKEN` с именем коллеги (тест с двумя потоками).
* Отмена клиентом во время обработки: воркер делает внешние вызовы вне транзакции, а переход выполняет с прочитанной версией; если клиент успел отменить, переход отклоняется, результат задачи отбрасывается, заявка остается `CANCELLED`.
* Дубликат активной заявки: частичный уникальный индекс на ИНН и продукт для нетерминальных статусов.

## 3. Таймауты и повторы

| Взаимодействие | Таймаут | Быстрые повторы | Отложенные повторы | Исход |
|---|---|---|---|---|
| Источники обогащения | `SOURCE_TIMEOUT_SECONDS` = 5 с | до 3 попыток, паузы 1, 2 с (`SOURCE_FAST_RETRY_DELAYS`) | 30 с, 1, 2, 5, 10 мин (`ENRICHMENT_RETRY_SCHEDULE`), только неответившие источники, успешные ответы сохраняются | `EXTERNAL_SERVICE_UNAVAILABLE`, затем `PROCESSING_ERROR` с `failed_stage = ENRICHMENT` |
| Автозаполнение по ИНН | 5 с | нет | при обработке заявки | клиент продолжает без автозаполнения |
| ЭДО, АБС | 10 с | до 3 попыток | ручной `RETRY_PROCESSING` | `PROCESSING_ERROR` (`EDO_FAILED`, `ABS_FAILED`) |
| Задача воркера (непредвиденная ошибка) | | экспоненциальная задержка, до 5 попыток | | `PROCESSING_ERROR` (`UNEXPECTED`) |
| Модель ИИ | 10 с | нет | | шаблон |
| БД | `statement_timeout` 15 с, `pool_pre_ping` | | | ошибка запроса, воркер продолжает цикл |

Ответ "нет данных" (404 источника) считается успешным. Клиент в технических статусах видит `CHECKING` с текстом о задержке, сотрудник видит `failed_stage`, `last_error_code`, все попытки по источникам и вкладку "Ошибки обработки". Повтор `RETRY_PROCESSING` сбрасывает счетчики и ставит задачу этапа заново. При `SOURCE_INVALID_RESPONSE` на скоринге или принятии решения повтор начинается с `ENRICHMENT`, чтобы получить отсутствующие или устаревшие данные до нового расчета.

## 4. Таймеры

Цикл воркера раз в `TIMER_INTERVAL_SECONDS` (по умолчанию 15 с; фактическая задержка зависит от рабочего цикла): повтор обогащения, истечение предложения (`OFFER_PENDING`, `SIGNING`), уведомление за 24 часа до истечения, истечение дозапроса, истечение черновика, флаг нарушения SLA ручного рассмотрения, аннулирование просроченных кодов подписания (текст кода удаляется из уведомления), возврат зависших задач, отметка опубликованных событий outbox, очистка ключей идемпотентности старше 24 часов. Сроки берутся из `policy.v1.json` и для демо сокращаются переменными окружения (`OFFER_TTL_SECONDS` и другие).

## 5. Масштабирование

* **api** без состояния: сессия в JWT, ключ подписи общий (переменная или `system_secrets`), идемпотентность и лимиты в БД. Реплики добавляются за nginx.
* **worker**: поддерживаются несколько процессов (`WORKER_REPLICAS`): задача достается одному через `FOR UPDATE SKIP LOCKED`, таймеры обрабатывают каждую заявку под блокировкой строки с пропуском занятых, переходы условные.
* **PostgreSQL**: пул соединений на процесс (`DB_POOL_SIZE`), индексы под очередь, таймеры и списки. Предложено, не реализовано: PgBouncer, реплика для чтения метрик, партиционирование `events` и `jobs` по времени, вынос событий в брокер из outbox.

## 6. Наблюдаемость

D04 реализовано: healthcheck API обращается к `/api/health/ready` (БД и загруженные конфиги). Healthcheck worker проверяет доступ к БД, загрузку конфигов и свежесть heartbeat, обновляемого рабочим циклом. Порог свежести связан с `JOB_LEASE_SECONDS`; это не проверка конкретной бизнес-задачи. Доступность порта metrics сама по себе не доказывает работу цикла. Результаты проверок: [audit-fixes.md](../testing/audit-fixes.md).

* **Логи** в JSON (stdout, ротация json-file): время, уровень, сервис, `request_id`, пользователь и роль, маршрут как шаблон (без ИНН в пути), статус, длительность; ИНН в сообщениях маскируется. `X-Request-Id` проходит через api, воркер (`correlation_id` задачи) и симулятор.
* **Метрики Prometheus**: api `/metrics` (запросы и задержки по маршрутам, переходы T-xx, события, внешние вызовы по системе и исходу), воркер `:9100/metrics` (задачи по исходу, длительность, глубина очереди).
* **Health checks**: `/api/health/live` (процесс), `/api/health/ready` (БД и конфиги ожидаемых версий); healthcheck долговременных сервисов в compose; `migrate` одноразовый и должен завершиться с кодом 0, `depends_on` с условиями `service_healthy` и `service_completed_successfully`.
* **Бизнес-мониторинг**: экран метрик риск-менеджера по журналу событий (надежность интеграций, ретраи, заявки в ошибке, SLA).

## 7. Миграции и запуск

Миграции Alembic выполняет один одноразовый сервис `migrate` до старта api и воркера (никакая реплика не мигрирует схему сама). Seed идемпотентен и выполняется под advisory lock. Конфиги проверяются при старте. Корректная остановка воркера по SIGTERM: текущая задача завершается.

## 8. Предложено: условия дальнейшей эксплуатации

* резервное копирование и PITR PostgreSQL, проверка восстановления; репликация и отказоустойчивый кластер;
* алерты (очередь растет, задачи в `FAILED`, заявки в `PROCESSING_ERROR`, нарушения SLA, ошибки интеграций) и трассировка OpenTelemetry;
* circuit breaker для внешних систем и квоты запросов к ним;
* согласованный с реальным провайдером протокол сверки операций с неизвестным исходом и регламент ручного разбора; реализованный повтор по durable-запросу и ключу ограничен контрактами симулятора;
* брокер событий для внешних потребителей (из существующего outbox), хранение журнала в отдельном хранилище;
* нагрузочное тестирование и лимиты ресурсов по результатам; blue-green выпуск с миграциями expand-and-contract.
