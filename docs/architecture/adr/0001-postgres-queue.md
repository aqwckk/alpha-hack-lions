# ADR-0001. Очередь задач и таймеры на PostgreSQL

Статус: принято. Дата: 2026-10-23.

## Контекст

Конвейер асинхронный: после отправки заявки воркер выполняет проверку полноты, обогащение из пяти источников, скоринг, решение, подготовку документов и выдачу. Нужны повторы при сбоях, отложенные повторы по расписанию, таймеры истечения (предложение, дозапрос, черновик, SLA) и гарантия, что задача не потеряется и не выполнится дважды. Смена статуса и постановка следующей задачи должны быть атомарными. Запуск на обычном ПК одной командой.

## Решение

Таблица `jobs` в той же PostgreSQL. Задача ставится в той же транзакции, что и переход статуса (transactional outbox для команд). Воркер забирает задачу запросом `UPDATE jobs SET status = 'RUNNING' ... WHERE id = (SELECT id ... FOR UPDATE SKIP LOCKED LIMIT 1)`. Ошибка задачи: повтор с экспоненциальной задержкой (`JOB_BACKOFF_BASE_SECONDS * 2^(attempt-1)`), после `JOB_MAX_ATTEMPTS` заявка переходит в `PROCESSING_ERROR` с кодом `UNEXPECTED`. Зависшие задачи (процесс упал) возвращаются в очередь по истечении аренды `JOB_LEASE_SECONDS`. Таймеры работают в цикле воркера раз в `TIMER_INTERVAL_SECONDS` и обрабатывают каждую заявку в отдельной транзакции с `FOR UPDATE SKIP LOCKED`. Каждая задача хранит ожидаемый статус и при несовпадении завершается без действий.

## Альтернативы

* Redis/RabbitMQ + Celery: еще один компонент, двухфазная запись (статус в БД, сообщение в брокер) и риск рассинхронизации без outbox.
* Фоновые задачи внутри api: теряются при перезапуске, не масштабируются отдельно.

## Последствия

* Плюсы: одна транзакция для статуса, события, уведомления и задачи; нет потерянных и дублирующихся задач; несколько воркеров без координатора; очередь видна SQL-запросом.
* Минусы: пропускная способность ограничена БД (для прототипа и тысяч заявок в час достаточно); опрос очереди раз в секунду. При росте: `LISTEN/NOTIFY` для пробуждения, партиционирование `jobs`, вынос событий в брокер через существующий outbox.
