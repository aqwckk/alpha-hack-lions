# ADR-0002. Стейт-машина заявки как декларативная таблица и одна точка смены статуса

Статус: принято. Дата: 2026-10-23.

## Контекст

Спецификация [application-states.md](../../process/application-states.md) задает 20 статусов и 46 переходов с ролями и условиями, запрещенные переходы и требование показывать кнопки только из `available_actions`. Ошибка в одном обработчике (пропущенная проверка роли или статуса) ломает смысл процесса: выдача без подписи, решение не исполнителем, переход из терминального статуса.

## Решение

* Таблица `TRANSITIONS` в `app/domain/statemachine.py`: id перехода, исходные статусы, целевой статус, триггер (команда или системное событие), допустимые типы исполнителей, именованные guards (`owner`, `assignee`, `not_proposer`, `offer_not_expired`, `has_scoring`, `failed_before_decision` и другие).
* Единственная функция смены статуса `apply_transition()` (`app/services/core.py`): находит переход в таблице, проверяет исполнителя, guards и `expected_version`, выполняет `UPDATE applications ... WHERE id = :id AND status = :from AND version = :expected`, пишет `status_history`, событие `STATUS_CHANGED` и аудит. Остальные эффекты (доменные события, уведомления, задачи) добавляются в ту же транзакцию.
* `available_actions` строится из той же таблицы и тех же guards под роль и пользователя.
* Данные-guards (обязательные поля, согласия, границы продукта) проверяют обработчики команд до вызова `apply_transition()`.

## Последствия

* Запрещенный переход невозможно выполнить: его нет в таблице. Параметризованный тест проверяет разрешенные и запрещенные переходы раздела 8 и действия по ролям.
* Гонки решаются базой: из двух одновременных команд с одной версией проходит одна, вторая получает `409`.
* Добавление перехода: строка в таблице и обработчик эффектов; изменение процесса начинается со спецификации.
