# ADR-0005. Аутентификация и авторизация

Статус: принято. Дата: 2026-10-23.

## Контекст

Техлид зафиксировал JWT с ролями. Нужны тестовые учетные записи без внешних провайдеров, короткая сессия, отзыв, защита от перебора и проверка доступа к объекту: клиент видит только заявки своих компаний, сотрудник действует в пределах роли и назначения.

## Решение

* Пароли: argon2id (`argon2-cffi`), сравнение с фиктивным хешем для несуществующих логинов, одинаковый ответ на любую ошибку входа; 5 неудачных попыток на логин за минуту и лимит на IP (`429`).
* Access-токен: JWT HS256 на 30 минут, фиксированный алгоритм при проверке, обязательные `exp`, `iat`, `sub`, `iss`, `aud`, `jti`, тип `access`. Ключ из `JWT_SECRET` (не короче 32 символов) или случайный ключ, созданный один раз в `system_secrets`. Роль и пользователь сверяются с БД при каждом запросе (деактивация действует сразу).
* Refresh-токен: случайный, хранится только его sha256, HttpOnly cookie с `SameSite=Strict` и путем `/api/v1/auth`, одноразовый с ротацией; повтор использованного токена отзывает всю цепочку.
* Токен передается в заголовке `Authorization`, поэтому CSRF для API не применим; CORS разрешен только для своих origin (`CORS_ORIGINS`).
* Авторизация на трех уровнях: роль эндпоинта, объект (клиентский запрос к чужой заявке дает `404`, сотрудник видит заявки своих вкладок, черновики не видит никто из сотрудников), guards перехода (исполнитель, не автор проекта решения).

## Последствия

* api без состояния сессии, масштабируется горизонтально.
* Нет MFA и восстановления пароля: учетные записи демо создаются seed; для промышленной эксплуатации нужен корпоративный IdP (OIDC) для сотрудников и вход клиента через интернет-банк.
