# Роли и права доступа

Реализация отдельных возможностей и исключения зафиксированы в [реестре статусов](../product/implementation-status.md). Требования и критерии этого документа не являются отчетом об успешной проверке всех сценариев.

Статус: **предложено: спецификация MVP**. Права проверяются на бэкенде для каждой команды и каждого чтения; интерфейс только скрывает недоступные действия (по полю `available_actions`, см. [application-states.md](application-states.md), раздел 10).

## 1. Роли

| Код роли | Кто это | Персона | Задача в продукте |
|---|---|---|---|
| `CLIENT` | представитель малого бизнеса: собственник, директор, финансовый директор, бухгалтер, уполномоченный сотрудник | P1-P5 | подобрать продукт, подать заявку, ответить на дозапрос, выбрать условия, подписать |
| `UNDERWRITER` | кредитный аналитик / андеррайтер банка | B1 | рассмотреть нестандартные заявки, дозапросить данные, принять решение в пределах полномочий, разобрать заявки с ошибкой обработки |
| `RISK_MANAGER` | риск-менеджер / руководитель кредитного направления | B2 | подтверждать решения по принципу 4 глаз, видеть все заявки, метрики, версии скоринговой карты и политики, журнал аудита |

**Решение D-05: отдельной роли `ADMIN` в MVP нет.** Пользователи создаются начальными данными (seed), конфиги скоринга и политики загружаются из файлов репозитория, редактора политики в интерфейсе нет. Административные функции чтения (журнал, версии, метрики) и технический повтор обработки выполняет `RISK_MANAGER`. Управление пользователями и публикация политики из интерфейса не входят в MVP; расширение ролей не принято к реализации.

**Один пользователь `CLIENT` в MVP совмещает роли "заполняет" и "подписывает"** (исследование, C7 отложено). Он заявляет полномочия отдельным согласием `AUTHORITY_CONFIRMATION`; система не проверяет доверенность или право подписи. P4 покрыт только в части подготовки: отдельная передача руководителю, согласование и подпись другим пользователем не реализованы. Пользователь может подавать заявки по разным ИНН (например, бухгалтер на аутсорсе), владение заявкой определяется `client_user_id`.

| `ACCEPT_OFFER` | + | - | - | `OFFER_PENDING` | T-33 |

## 3. Какие заявки видит роль

| Роль | Список заявок | Карточка заявки |
|---|---|---|
| `CLIENT` | только свои, во всех статусах | только своя |
| `UNDERWRITER` | вкладки: "Очередь" (`MANUAL_REVIEW`, все), "Мои" (`IN_REVIEW` и `PENDING_RISK_APPROVAL` с `assignee_id` = он), "Ошибки обработки" (`PROCESSING_ERROR`, все), "Решенные мной" | заявки из своих вкладок; черновики (`DRAFT`) не видны никому из сотрудников |
| `RISK_MANAGER` | все заявки, кроме `DRAFT`; вкладка "На согласовании" (`PENDING_RISK_APPROVAL`) | любая, кроме `DRAFT` |

Черновики не видны сотрудникам, потому что клиент еще не передал данные банку и не дал согласия на их рассмотрение. Каждое открытие карточки сотрудником пишет событие `APPLICATION_VIEWED` (кто, когда, какая заявка), это журнал доступа к персональным данным и банковской тайне.

## 5. Принцип 4 глаз

- Применяется к положительным решениям андеррайтера, если сумма варианта больше `underwriter_authority_limit` (исходно 50 000 000 руб.) или решение является переопределением рекомендации политики ([decision-model.md](decision-model.md), раздел 6).
- Андеррайтер формирует проект решения, заявка переходит в `PENDING_RISK_APPROVAL`; риск-менеджер подтверждает (`CONFIRM_DECISION`) или возвращает с комментарием (`RETURN_DECISION`).
- Проверка на бэкенде: `confirmed_by` не равен `proposed_by`, роль подтверждающего `RISK_MANAGER`.
- Отказы и дозапросы 4 глаз не требуют: они не создают кредитного риска для банка, а отказ всегда сопровождается кодом причины и обязательным комментарием.
- Приоритет MVP: Should. Без реализации T-28 процесс остается корректным (все ручные решения проходят по T-27).

## 6. Аутентификация и сессии (требования для бэкенда)

- Вход по логину и паролю тестовых учетных записей, JWT с ролью и `user_id`; срок жизни токена доступа 30 минут. Пароли хранятся только в виде хеша.
- Роль берется только из токена, выданного сервером; параметры запроса не влияют на роль.
- Ошибки: `401` без токена или с истекшим токеном; `403` при недостаточной роли для действия или если сотрудник не является исполнителем заявки (`NOT_ASSIGNEE`); `404` при обращении клиента к чужой заявке; `409` при недопустимом переходе или конфликте версий.
- События безопасности `USER_LOGGED_IN`, `LOGIN_FAILED` пишутся в журнал аудита без пароля.
- Тестовые учетные записи (по одной на сценарий демо и по сотрудникам) создаются seed-скриптом, список приводится в README и в [../product/demo-scenarios.md](../product/demo-scenarios.md).

## 7. Обязательные тесты прав

1. Клиент A не получает заявку клиента B ни в списке, ни по id (`404`).
2. Клиент не может выполнить `TAKE`, `APPROVE`, `DECLINE`, `REQUEST_INFO` (`403`).
3. Андеррайтер, не являющийся `assignee`, не может принять решение по `IN_REVIEW` (`403 NOT_ASSIGNEE`).
4. Андеррайтер не видит черновики и не может изменить анкету клиента.
5. Риск-менеджер не может подтвердить проект решения, автором которого является он сам.
6. В клиентском API нет полей `score`, `grade`, `pd`, `factor_contributions`, `rules_fired`, `recommendation`, `status` (внутренний), внутренних комментариев.
