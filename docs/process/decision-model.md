# Модель кредитного решения (продуктовая часть)

Статус документа: **принято для реализации MVP**. Числовые пороги, баллы скоринговой карты и калибровка заполняются аналитиком в `analytics/` (конфиги скоринговой карты и политики). Здесь зафиксировано, **какие** правила применяются, **в каком порядке**, **какие параметры** должны быть конфигурируемыми и **какими кодами** объясняется решение.

Связанные документы: [application-states.md](application-states.md) (статусы `SCORING` и `DECISIONING`), [../product/product-catalog.md](../product/product-catalog.md) (параметры продуктов), [data-requirements.md](data-requirements.md) (данные), исследование [../research/01-domain.md](../research/01-domain.md) (раздел 7) и [../research/08-recommendations-for-mvp.md](../research/08-recommendations-for-mvp.md) (раздел 6).

## 1. Скоринг и политика: разделение

| | Скоринг (оценка риска) | Кредитная политика (решение) |
|---|---|---|
| Вопрос | насколько вероятно, что заемщик не вернет долг | что банк предлагает: выдать, сколько, на какой срок, какой продукт, или отказать, или запросить данные |
| Этап и статус | `SCORING`, задача `SCORE` | `DECISIONING`, задача `DECIDE` |
| Вход | признаки заемщика из анкеты и источников | балл и грейд, параметры заявки, параметры продукта, стоп-факторы, долговая нагрузка, полномочия |
| Выход | `score` (целое), `grade` (A, B, C, D, E; A лучший), `pd` по грейду, вклад каждого фактора | результат (раздел 2), коды причин, варианты предложения, сработавшие правила, рекомендация для андеррайтера |
| Конфиг | `scorecard` (версия `scorecard_version`) | `policy` с разделом `products` (версия `policy_version`) |
| Владелец | аналитик / риск-методология | риск-менеджер |
| Частота изменений | редко, с валидацией (Gini, PSI) | чаще: пороги, лимиты, ставки |
| Зависимость | ничего не знает о продукте и сумме запроса, кроме факторов, явно включенных аналитиком | не вычисляет балл, использует готовый грейд |

Каждое решение хранит обе версии (`scorecard_version`, `policy_version`), поэтому любое решение можно воспроизвести и объяснить.

**Скоринг рассчитывается всегда, даже если затем сработает стоп-фактор.** Балльная карта вычисляется за миллисекунды, а балл по отклоненным заявкам нужен аналитику для оценки стабильности модели и андеррайтеру для контекста. Стоп-факторы являются частью политики и применяются первым правилом (POL-01), поэтому разделение "оценка риска отдельно, решение отдельно" сохраняется.

## 2. Результаты решения

| Код результата | Смысл | Статус после решения | Кто может принять |
|---|---|---|---|
| `APPROVED` | банк готов выдать на запрошенных условиях | `OFFER_PENDING` | политика (авто), андеррайтер |
| `COUNTER_OFFER` | банк готов выдать на других условиях: меньшая сумма, больший срок или другой продукт | `OFFER_PENDING` | политика (авто), андеррайтер |
| `NEEDS_INFO` | для решения не хватает данных от клиента | `INFO_REQUESTED` | политика (авто), андеррайтер |
| `MANUAL_REVIEW` | автоматическое решение недопустимо, нужен специалист | `MANUAL_REVIEW` или `IN_REVIEW` | только политика |
| `DECLINED` | банк не выдает кредит | `DECLINED` | политика (авто), андеррайтер |

Поле `mode` решения: `AUTO` (политика) или `MANUAL` (андеррайтер). Для продукта с режимом `MANUAL` (инвестиционный кредит) автоматически возможны только `DECLINED` по стоп-фактору или грейду, `NEEDS_INFO` и `MANUAL_REVIEW`; любое положительное решение принимает человек.

## 3. Правила политики в порядке применения

Политика выполняется как упорядоченный список правил. Правила POL-01...POL-03 и POL-05...POL-07 завершают выполнение при срабатывании (кроме POL-05, которое собирает все причины ручного рассмотрения). Каждое сработавшее или проверенное правило записывается в `rules_fired` решения с результатом и значениями входов, чтобы андеррайтер и риск-менеджер видели, почему получен исход.

| ID | Правило | Условие (параметры конфигурируемые) | Результат | Коды причин |
|---|---|---|---|---|
| POL-01 | Стоп-факторы | любой из: субъект не найден в реестре; статус из `blocked_company_statuses`; возраст бизнеса меньше `min_business_age_months` продукта; признаки из `unreliable_flags`; текущая просрочка в БКИ не меньше `current_delinquency_min_days`; налоговая недоимка не меньше `tax_arrears_stop_amount`; комплаенс-флаг | `DECLINED` (проверяются все стоп-факторы, в решение попадают все сработавшие) | `SF_*` |
| POL-02 | Подтверждение дохода | нет ни оборотов по счету в банке, ни отчетности ГИР БО, и клиент еще не приложил выписку `BANK_STATEMENT` | `NEEDS_INFO`, если `auto_info_request_count < max_auto_info_cycles`; иначе `MANUAL_REVIEW` | `NI_INCOME_NOT_CONFIRMED` или `MR_INFO_CYCLES_EXCEEDED` |
| POL-03 | Минимальный грейд | грейд входит в `decline_grades` продукта | `DECLINED` | `DCL_LOW_SCORE` |
| POL-04 | Расчет долговой нагрузки | всегда (без исхода): считаются подтвержденный доход, допустимый платеж, запрошенный платеж, максимальные суммы (раздел 4) | промежуточные значения | |
| POL-05 | Причины ручного рассмотрения | собираются все: режим продукта `MANUAL`; грейд в `gray_grades`; сумма больше `auto_approval_limit` (кроме продуктов с режимом `MANUAL`, где эту роль играет первая причина); заявленная выручка выше подтвержденной больше чем на `revenue_mismatch_threshold`; недоимка больше 0, но меньше `tax_arrears_stop_amount`; доход подтвержден только выпиской клиента; покрытие залогом ниже `min_collateral_coverage`; `manual_review_required = true` | `MANUAL_REVIEW`, если найдена хотя бы одна причина; рассчитывается рекомендация (раздел 6) | `MR_*` |
| POL-06 | Одобрение | запрошенный платеж не больше допустимого | `APPROVED`; ставка из матрицы; при цели из `credit_line_suggest_purposes` добавляется альтернативный вариант "кредитная линия" (Should) | нет (или `CO_PRODUCT_ALTERNATIVE` для альтернативы) |
| POL-07 | Контрпредложение | запрошенный платеж больше допустимого | `COUNTER_OFFER`, если построен хотя бы один вариант (раздел 5); иначе `DECLINED` | `CO_DEBT_LOAD`, `CO_PRODUCT_ALTERNATIVE` или `DCL_AFFORDABILITY` |

Почему такой порядок:

1. **Стоп-факторы первыми**: это жесткие ограничения, при которых условия не имеют смысла. Клиент получает ответ сразу, а не после ручной очереди.
2. **Подтверждение дохода до грейда**: без подтвержденной выручки нельзя честно посчитать ни нагрузку, ни часть факторов скоринга.
3. **Отказ по грейду до ручного рассмотрения**: андеррайтер не тратит время на заявки, которые политика в любом случае не допускает.
4. **Ручное рассмотрение до авторешения**: если есть признак нестандартности, автоматическое одобрение недопустимо, даже если нагрузка в норме.
5. **Контрпредложение вместо отказа**: если риск приемлем, но не проходит нагрузка, банк ищет допустимые условия (гипотеза H6).

## 4. Расчет долговой нагрузки (POL-04)

Все денежные расчеты в `Decimal`, округление `ROUND_HALF_UP` до копеек; суммы вариантов округляются вниз до `amount_rounding` (10 000 руб.).

| Величина | Формула |
|---|---|
| Подтвержденная месячная выручка `income_confirmed` | первый доступный источник по `income_source_priority`: средние поступления по счету за 12 мес (`BANK_TURNOVER`), выручка за последний год из ГИР БО / 12 (`FINANCIAL_STATEMENTS`), заявленная выручка, если приложена выписка (`BANK_STATEMENT`, проверяет специалист) |
| Расхождение `revenue_mismatch` | (заявленная выручка минус `income_confirmed`) / `income_confirmed`; считается, только если есть источник, отличный от заявления клиента |
| Доход для расчета `income_for_dti` | минимум из заявленной и подтвержденной выручки (консервативно) |
| Текущие платежи `existing_payments` | максимум из заявленных клиентом и ежемесячных платежей по данным БКИ |
| Допустимый платеж `allowed_payment` | `income_for_dti` x `max_debt_load_by_grade[grade]` минус `existing_payments` (не меньше 0) |
| Ставка `rate` | `base_rate_percent` продукта + `rate_premium_by_grade[grade]` |
| Запрошенный платеж `requested_payment` | аннуитет(сумма, `rate`, срок) по формуле из [product-catalog.md](../product/product-catalog.md), раздел 5 |
| Максимальная сумма на срок n `max_amount(n)` | `allowed_payment` x (1 - (1 + i)^(-n)) / i, где i = `rate` / 12 / 100; ограничивается `amount_max` продукта |

Упрощение (описано в [../product/assumptions.md](../product/assumptions.md)): нагрузка считается как доля платежей в выручке, а не в денежном потоке или прибыли.

## 5. Как формируется контрпредложение (POL-07)

Строятся до `max_counter_options` (3) вариантов в фиксированном порядке. Вариант включается, только если проходит все условия.

| Тип варианта `option_type` | Как считается | Условия включения |
|---|---|---|
| `AMOUNT_REDUCED` (меньшая сумма) | тот же продукт и срок, сумма = `max_amount(запрошенный срок)` | сумма не меньше `amount_min` продукта и не меньше `counter_offer_min_share` (исходно 0,3) от запрошенной; не больше `auto_approval_limit` (в режиме рекомендации для специалиста не применяется) |
| `TERM_EXTENDED` (больший срок) | тот же продукт и сумма, срок = минимальный n от запрошенного + 1 до `term_max_months`, при котором аннуитет не больше `allowed_payment` | такой срок существует |
| `PRODUCT_CHANGED` (другой продукт: кредитная линия) | продукт `CREDIT_LINE`, лимит L = минимум из `max_amount(tranche_max_term_months)` по ставке линии, `amount_max` линии, запрошенной суммы и `auto_approval_limit` линии (последнее только в авторежиме); платеж варианта показывается как аннуитет всего лимита на `tranche_max_term_months`, срок договора равен запрошенному сроку в пределах срока линии | исходный продукт `EXPRESS` или `WORKING_CAPITAL`; цель входит в `allowed_purposes` линии; возраст бизнеса не меньше минимума линии; грейд не в `decline_grades` и не в `gray_grades` линии; L не меньше `amount_min` линии |

- Флаг `recommended = true` получает `TERM_EXTENDED`, если он есть (клиент получает всю сумму), иначе `AMOUNT_REDUCED`, иначе `PRODUCT_CHANGED`.
- Если ни один вариант не построен, результат `DECLINED` с кодом `DCL_AFFORDABILITY`.
- Клиент видит исходный запрос и варианты рядом: сумма, срок, ставка, ежемесячный платеж, переплата, требования (поручительство), и текст причины `CO_DEBT_LOAD`.
- Андеррайтер в ручном контрпредложении задает от 1 до 3 вариантов сам (форма заполняется вариантами из рекомендации политики); тип варианта `UNDERWRITER_TERMS`, если условия отличаются от рассчитанных; ставка берется из матрицы "продукт x грейд" и в MVP не редактируется.

**Кредитная линия** доступна клиенту только как вариант предложения (контрпредложение по POL-07 или альтернатива при одобрении по POL-06), а не как отдельная заявка. Обоснование в [../product/mvp-scope.md](../product/mvp-scope.md), решение D-01.

## 6. Рекомендация политики для ручного рассмотрения

Когда POL-05 направляет заявку специалисту, политика все равно выполняет POL-06 и POL-07 в режиме рекомендации (без ограничения `auto_approval_limit`, полномочия специалиста ограничены `underwriter_authority_limit`) и сохраняет `recommendation`: предлагаемый исход (`APPROVED`, `COUNTER_OFFER` или `DECLINED`), `allowed_payment`, `max_amount(запрошенный срок)` и рассчитанные варианты. Андеррайтер видит рекомендацию в карточке и может решить иначе.

**Переопределение (`override = true`)** фиксируется, если андеррайтер:

- одобряет или предлагает сумму больше `max_amount` для выбранного срока по рекомендации;
- одобряет заявку, у которой грейд входит в `decline_grades` (возможно только для заявок, пришедших в ручную очередь по `MR_INFO_CYCLES_EXCEEDED` до скоринга, поэтому на практике редкость).

Переопределение требует комментария и, если реализован принцип 4 глаз, подтверждения риск-менеджера ([application-states.md](application-states.md), раздел 7). Доля переопределений является метрикой качества риска ([events.md](events.md)).

Андеррайтер не может одобрить заявку без результата скоринга (заявка, попавшая в ручную очередь до обогащения, может быть только отклонена или направлена на дозапрос).

## 7. Какие данные влияют на решение

| Данные | Источник | Скоринг | Политика |
|---|---|---|---|
| Возраст бизнеса | ЕГРЮЛ / ЕГРИП | фактор (по решению аналитика) | стоп-фактор `SF_BUSINESS_AGE` по продукту |
| Статус субъекта, признаки недостоверности | ЕГРЮЛ / ЕГРИП, ФНС | нет | стоп-факторы `SF_COMPANY_STATUS`, `SF_UNRELIABLE_REGISTRY_DATA` |
| ОКВЭД (отрасль) | ЕГРЮЛ / ЕГРИП | фактор (группа риска отрасли) | нет |
| Налоговый режим, численность | ФНС | фактор (по решению аналитика) | нет |
| Налоговая недоимка | ФНС | фактор (по решению аналитика) | стоп-фактор или причина ручного рассмотрения |
| Выручка, прибыль, динамика | ГИР БО (ООО), обороты по счету | факторы | подтвержденный доход, расхождение с анкетой |
| Кредитная история: просрочки текущие и исторические, число запросов, платежи | БКИ | факторы | стоп-фактор `SF_CURRENT_DELINQUENCY`, текущие платежи в нагрузке |
| Заявленная выручка и текущие платежи | анкета | нагрузка как фактор (по решению аналитика) | нагрузка, расхождение |
| Продукт, сумма, срок, цель | анкета | нет (скоринг оценивает заемщика) | лимиты, авто-полномочия, нагрузка, варианты |
| Сведения о залоге | анкета, документы | нет | покрытие залогом, причина `MR_COLLATERAL_REVIEW` |
| Комплаенс-флаг | мок (синтетика) | нет | стоп-фактор `SF_COMPLIANCE` |

## 8. Конфигурируемые параметры

Все параметры ниже не задаются в коде. Исходные значения продуктов заданы в [../product/product-catalog.md](../product/product-catalog.md); значения, помеченные "аналитик", определяет и калибрует аналитик. Действующие значения и обоснование: [../analytics/decision-policy.md](../analytics/decision-policy.md), конфиги `analytics/artifacts/scorecard.v1.json` и `analytics/artifacts/policy.v1.json`.

### 8.1. Скоринговая карта (`scorecard`, владелец: аналитик)

| Параметр | Описание |
|---|---|
| `version`, `created_at`, `author` | версия и происхождение |
| `factors[]` | код фактора, источник, правила разбиения на интервалы (bins), баллы за интервал, значение для "нет данных" |
| `base_points` | базовый балл |
| `grade_bands` | границы баллов для грейдов A, B, C, D, E |
| `pd_by_grade` | ожидаемая вероятность дефолта по грейду (для метрик и ожидаемых потерь) |

Выход скоринга для API и карточки: `score`, `grade`, `pd`, `factor_contributions[]` (код фактора, название для сотрудника, значение признака, интервал, баллы), `scorecard_version`.

### 8.2. Политика (`policy`, владелец: риск-менеджер, значения: аналитик)

| Параметр | Описание | Исходное значение |
|---|---|---|
| `version`, `effective_from`, `author` | версия политики | |
| `products.<CODE>.*` | параметры продуктов из каталога: `direct_application`, `applicant_types`, `allowed_purposes`, `amount_min`, `amount_max`, `amount_step`, `term_min_months`, `term_max_months`, `base_rate_percent`, `review_mode`, `auto_approval_limit`, `green_grades`, `gray_grades`, `decline_grades`, `min_business_age_months`, `requires_owner_guarantee_for`, `requires_collateral`, `min_collateral_coverage`, `required_documents`, `tranche_max_term_months` | см. каталог |
| `blocked_company_statuses` | статусы субъекта, при которых отказ | `LIQUIDATING`, `BANKRUPTCY`, `REORGANIZING`, `CEASED` |
| `unreliable_flags` | признаки недостоверности | `UNRELIABLE_ADDRESS`, `UNRELIABLE_DIRECTOR`, `MASS_ADDRESS`, `MASS_DIRECTOR`, `DISQUALIFIED_DIRECTOR` |
| `current_delinquency_min_days` | порог текущей просрочки для стоп-фактора | 30 (аналитик) |
| `tax_arrears_stop_amount` | порог недоимки для отказа | 100 000,00 руб. (аналитик) |
| `max_debt_load_by_grade` | максимальная доля платежей в месячной выручке по грейдам A-E | 0,30 / 0,25 / 0,20 / 0,15 / 0,10 (аналитик) |

| `income_source_priority` | порядок источников дохода | `BANK_TURNOVER`, `FINANCIAL_STATEMENTS`, `BANK_STATEMENT` |
| `min_turnover_months` | минимум месяцев оборотов, чтобы они подтверждали доход | 6 (аналитик) |
| `compliance_stop_flags` | значения комплаенс-флага, дающие `SF_COMPLIANCE` | `RED` |
| `counter_offer_min_share` | минимальная доля от запрошенной суммы для варианта `AMOUNT_REDUCED` | 0,3 |
| `max_counter_options` | максимум вариантов в предложении | 3 |
| `amount_rounding` | шаг округления сумм вариантов вниз | 10 000 руб. |
| `credit_line_suggest_purposes` | цели, при которых к одобрению добавляется альтернатива "кредитная линия" | `SEASONAL_PURCHASES`, `CASH_GAP` |
| `underwriter_authority_limit` | сумма, выше которой решение андеррайтера требует 4 глаз | 50 000 000 руб. |
| `override_requires_risk_approval` | требовать 4 глаза при переопределении | `true` |
| `max_auto_info_cycles` | максимум автоматических дозапросов | 3 |
| `offer_ttl_days` | срок действия предложения | 7 |
| `info_response_ttl_days` | срок ответа на дозапрос | 14 |
| `draft_ttl_days` | срок жизни неактивного черновика | 30 |
| `manual_review_sla_hours` | SLA ручного рассмотрения | 8 |

### 8.3. Технические параметры (не политика, переменные окружения)

Таймауты источников (5 сек), число и паузы быстрых повторов (3; 1, 2, 4 сек), расписание отложенных повторов обогащения (30 сек, 1, 2, 5, 10 мин), срок кеша ответов источников (24 ч), TTL кода подписания (5 мин) и число попыток (3), повторы ЭДО и АБС (3), период планировщика таймеров (15 сек).

## 9. Справочник кодов причин

Один справочник используется в решениях, дозапросах, отменах и в интерфейсе. Коды стабильны и хранятся в БД; тексты хранятся в справочнике (таблица или JSON), а не в коде фронтенда, чтобы их можно было менять без релиза. В фигурных скобках подставляемые значения.

Видимость для клиента: **FULL** (показывается текст для клиента с подстановками), **GENERIC** (показывается только общий текст, детали скрыты по требованиям комплаенса), **NONE** (клиент не видит код, видит общий текст своего клиентского статуса).

Правило показа нескольких причин: клиенту показываются все причины с видимостью FULL в порядке справочника; если среди причин есть причина с видимостью GENERIC, показывается только ее текст. Внутренние пороги, балл, грейд и допустимый платеж клиенту не показываются никогда.
