# Тестовые сценарии

Документ отвечает на два вопроса: что проверяется автоматически и как вручную пройти основной сценарий через интерфейс.

Принцип: тестов мало, каждый закрывает отдельный риск на самом дешевом уровне, который его доказывает. Однотипные случаи собраны в параметризованные тесты, одна и та же проверка не повторяется на разных уровнях.

## 1. Автоматические проверки

| Уровень | Команда | Что доказывает |
|---|---|---|
| Бэкенд, pytest против PostgreSQL 17 | `make test` | 27 тестовых функций, 155 случаев с параметризацией |
| Фронтенд, Vitest + RTL + MSW | `make web-test` | typecheck, 29 тестов в 11 файлах, production-сборка |
| Сквозной сценарий через API живого стека | `make e2e` | сценарии S1-S5 и проверка прав на собранном `docker compose` |
| Воспроизводимость аналитики | `cd analytics && uv run --python 3.12 python -m src.build_all` | конфиги, golden-файл и история пересобираются побитно; сборка падает, если путь правил демо-профиля изменился |
| Границы аналитических метрик | `cd analytics && uv run --python 3.12 --frozen python -m unittest discover -s tests -v` | 2 теста: одинаковые баллы и перестановки для KS, пустые подгруппы метрик |
| Переносимость checkout | `python3 scripts/check_checkout.py` | хеши scorecard/policy и LF скриптов; в CI выполняется на Windows с `core.autocrlf=true` |

Изменения D01-D16 и конкретные граничные проверки перечислены в [реестре исправлений](audit-fixes.md).

### 1.1. Бэкенд (`services/api/tests`)

| Риск | Тест | Что проверяется |
|---|---|---|
| Расхождение скоринга и политики с моделью аналитика | `test_golden.py::test_scoring_and_policy_match_golden` | 63 эталонных случая из `analytics/artifacts/expected_outcomes.json`: версии и sha256 конфигов, балл, грейд, PD, баллы факторов, исход, reason codes, путь правил, варианты контрпредложения |
| Заявка перескакивает этап или застревает | `test_state_machine.py::test_allowed_transitions`, `test_forbidden_transitions` | разрешенные переходы T-xx и запрещенные (из терминальных статусов, в обход проверок) |
| Кнопки в интерфейсе не совпадают с правами | `test_state_machine.py::test_available_actions_by_role` | `available_actions` по ролям и статусам |
| Обход стейт-машины через API | `test_state_machine.py::test_api_rejects_transition_outside_table` | команда вне таблицы отклоняется с 409 |
| Клиент видит чужие данные | `test_authorization.py::test_foreign_client_gets_404` | чужая заявка недоступна по всем ресурсам |
| Клиент выполняет действия сотрудника | `test_authorization.py::test_client_cannot_run_employee_commands` | 403 на команды андеррайтера и риск-менеджера |
| Утечка внутренних данных риска | `test_authorization.py::test_client_view_has_no_internal_risk_data` | в клиентском ответе нет score, grade, рекомендации и порогов |
| Решение принимает не тот сотрудник | `test_authorization.py::test_underwriter_does_not_see_drafts_and_non_assignee_cannot_decide` | черновики скрыты от банка, решать может только взявший в работу |
| Двойная отправка и устаревшие данные | `test_concurrency.py::test_double_submit_and_stale_version` | Idempotency-Key дает один результат, устаревший `expected_version` дает 409 |
| Два андеррайтера берут одну заявку | `test_concurrency.py::test_take_race_has_one_winner` | ровно один победитель, второй получает `ALREADY_TAKEN` |
| Отмена клиентом во время обработки | `test_concurrency.py::test_withdraw_wins_over_running_task` | задача воркера не перезаписывает отмену |
| Сбой внешнего сервиса | `test_worker.py::test_source_failure_retries_and_recovers` | временный сбой БКИ лечится ретраем; полное отключение ведет в `EXTERNAL_SERVICE_UNAVAILABLE` и восстанавливается повтором |
| Разрыв сквозного процесса | `test_end_to_end.py::test_investment_loan_from_draft_to_issued` | инвестиционный кредит от черновика до `ISSUED`: дозапрос, ручное рассмотрение, 4 глаза, подписание; повторное подписание не создает вторую выдачу |

### 1.2. Фронтенд (`web/src`)

| Риск | Что проверяется |
|---|---|
| Ошибка в ИНН уходит на сервер | контрольная сумма ИНН ЮЛ и ИП |
| Кнопка действия, недоступного по процессу | кнопки строятся только из `available_actions` |
| Пользователь работает с устаревшей заявкой | 409 `VERSION_CONFLICT` перечитывает заявку и объясняет, что произошло |
| Потеря черновика | автосохранение отправляет только измененное поле с актуальной версией |
| Неверный выбор в предложении | рекомендуемый вариант выбран, принятие отправляет `option_id`, версию и новый Idempotency-Key |
| Выход из сессии посреди работы | истекший access-токен обновляется один раз и запрос повторяется |

### 1.3. Сквозной e2e (`scripts/e2e_demo.py`)

Скрипт работает только через публичный API, как браузер, и сравнивает каждый шаг с ожидаемым исходом из [demo-scenarios.md](../product/demo-scenarios.md). Запуск: `make e2e` (API на 8000) или `E2E_BASE_URL=http://localhost:8080/api python3 scripts/e2e_demo.py` (через nginx фронтенда). Повторный запуск безопасен.

| Сценарий | Ожидаемый результат |
|---|---|
| S1 | экспресс-кредит ИП одобрен автоматически, подписан, выдан |
| S2 | контрпредложение с тремя вариантами, клиент выбирает вариант, выдача |
| S3 | ручное рассмотрение, дозапрос, ответ клиента, одобрение с переопределением, 4 глаза, выдача |
| S4 | отказ по стоп-факторам, клиенту показан понятный текст без порогов |
| S5 | таймауты БКИ, автоматический ретрай, одобрение |
| AUTHZ | клиент не видит чужую заявку и не может выполнить команды сотрудника |

## 3. Что не покрыто автоматически

- Браузерные автотесты (Playwright): основной путь закрыт e2e по API и ручной проверкой S1, S2, S3 в браузере.
- Автоматическая проверка доступности (axe) и проверка с экранным диктором.
- Нагрузочное тестирование. Архитектурные предпосылки описаны в [reliability.md](../architecture/reliability.md).
- Профиль `ai` с локальной моделью: шаблонный режим проверен, запуск модели зависит от ресурсов машины.
