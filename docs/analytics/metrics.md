# Метрики экрана риск-менеджера (BK-06)

Эталонный расчет: [metrics.py](../../analytics/src/metrics.py). Воспроизводимые значения: [build_report.json](../../analytics/artifacts/build_report.json), раздел `history`. Ниже описано фактическое поведение этого расчета. Совпадение с текущим экраном и SQL бэкенда требует отдельной проверки.

## 1. Когорты, события и знаменатели

1. **Источник:** журнал событий, отсортированный по `occurred_at`. Когорта C состоит из уникальных заявок, чье первое `APPLICATION_CREATED` попало в полуоткрытое окно `[period_start, period_end)`. Временные метки имеют часовой пояс, в отчете используется UTC.
2. **Наблюдение за когортой:** расчет использует все переданные события заявок C, включая события после `period_end`. Конец окна ограничивает создание заявок, а не наблюдение за ними. Для среза на конкретную дату нужно предварительно ограничить журнал этой датой; у свежей когорты часть исходов еще не наступила. В сборке история ограничена `reference_now`.
3. **Отправленные S:** заявки C с хотя бы одним `APPLICATION_SUBMITTED`. Время заполнения берется из первого такого события.
4. **Первое итоговое решение F:** первое `DECISION_MADE` каждой заявки C с `outcome` в `APPROVED`, `COUNTER_OFFER`, `DECLINED`. `NEEDS_INFO` и `MANUAL_REVIEW` промежуточные. Для скорости и структуры исходов учитывается не больше одного решения на заявку. Для переопределений учитываются все ручные итоговые решения, включая повторные.
5. **SLA North Star:** `time_from_submit_sec` из первого итогового решения сравнивается с `decision_sla_auto_minutes * 60` для `mode = AUTO` (900 секунд) или с `decision_sla_manual_hours * 3600` для ручного решения (86 400 секунд). Равенство входит в SLA. Это календарные 24 часа, без рабочего календаря. Отсчет идет от отправки, хотя знаменатель включает все созданные заявки.
6. **Пустой знаменатель:** доли и среднее число циклов возвращают `null`; время заполнения при пустом S и медианы решения при пустом F также возвращают `null`. Автоматическая медиана возвращает `null` при отсутствии авторешений, даже если есть ручные итоговые решения. На экране для отсутствующих значений следует показывать "недостаточно данных". Доли округляются до 4 знаков, среднее число циклов до 3, медианы остаются в секундах.
7. **Границы реализации:** `compute_metrics` получает окно и SLA, но не имеет фильтра продукта. Для разбивки по продукту нужно заранее отобрать заявки и связанные события; сессии подбора требуют отдельного определения продуктовой когорты. Окна и фильтры экрана не следует считать проверенными этим отчетом.

## 2. North Star и клиентская воронка

**Измеряемая North Star: доля созданных заявок с первым итоговым решением в SLA.** Наличие решения и его длительность не подтверждают, что клиент увидел, понял объяснение или знает следующий шаг. Понятность остается отдельной продуктовой гипотезой: для ее проверки нужны ответы пользователей или исследование с проверкой понимания. `APPLICATION_VIEWED` и принятие предложения сами по себе этого не доказывают.

| Поле отчета / метрика | Числитель или наблюдения | Знаменатель / правило |
|---|---|---|
| `applications_created` | число заявок C | абсолютное число |
| `north_star` | первые итоговые решения F с `time_from_submit_sec <= SLA(mode)` | все заявки C, включая неотправленные и еще без решения |
| `time_to_decision_median_sec` | `time_from_submit_sec` решений F | медиана по F |
| `time_to_decision_auto_median_sec` | те же длительности для F с `mode = AUTO` | медиана только по авторешениям, `null` при пустой AUTO-подгруппе; отдельной ручной медианы в отчете нет |
| `wizard_conversion` | уникальные `wizard_session_id`, одновременно имеющие `PRODUCT_WIZARD_STARTED` в окне и `APPLICATION_CREATED` в C | уникальные сессии с `PRODUCT_WIZARD_STARTED` в окне; создание заявки вне окна не засчитывается |
| `fill_conversion` | заявки S | все заявки C |
| `fill_duration_median_sec` | `fill_duration_sec` первого `APPLICATION_SUBMITTED` каждой заявки S | медиана по S |
| `prefill_share` | сумма `fields_prefilled` всех `PREFILL_COMPLETED` заявок C | сумма `fields_total` тех же событий; повторные события также учитываются |
| `completeness_first_time` | заявки S без единого `COMPLETENESS_FAILED` в доступном журнале | заявки S; название означает отсутствие зарегистрированного сбоя, наличие `COMPLETENESS_PASSED` не проверяется |
| `info_request_share` | заявки S с хотя бы одним `INFO_REQUESTED`, независимо от `source` | заявки S |
| `info_request_cycles_avg` | все события `INFO_REQUESTED` заявок S с дозапросом | число таких заявок; заявки без дозапроса исключены |
| `offer_acceptance` | события `OFFER_ACCEPTED`, связанные по `offer_id` с учтенными предложениями | события `OFFER_ISSUED`, перед которыми последнее `DECISION_MADE` имеет исход `APPROVED` или `COUNTER_OFFER`, по заявкам C |
| `counter_offer_acceptance` | принятые предложения, у которых последнее решение перед выпуском было `COUNTER_OFFER` | выпущенные предложения с тем же исходом |
| `credit_line_chosen` | учтенные `OFFER_ACCEPTED` с `product_code = CREDIT_LINE` | абсолютное число по обоим типам предложения |
| `end_to_end_conversion` | заявки C с хотя бы одним `LOAN_ISSUED` | все заявки C; повторная выдача не увеличивает числитель |

Предложения считаются по событиям, а не по числу уникальных заявок: у заявки может быть несколько предложений. Прием связывается с уже выпущенным предложением той же заявки; варианты внутри одного предложения не увеличивают знаменатель. Для корректного журнала требуется по одному событию выпуска и приема на соответствующее действие: эталон не устраняет дубли событий. Последующее решение не меняет классификацию уже выпущенного предложения.

## 3. Операционные метрики

| Поле отчета / метрика | Числитель | Знаменатель / правило |
|---|---|---|
| `auto_decision_share` | решения F с `mode = AUTO` | все F |
| `manual_review_sla_share` | ручные решения F по заявкам без единого `REVIEW_SLA_BREACHED` в доступном журнале | ручные решения F; это отдельная метрика очереди, не сравнение длительности с 24 часами North Star |
| `outcomes` | решения F каждого итогового `outcome` | все F; отсутствующий исход может не попасть в словарь |
| `approval_rate` | F с `APPROVED` или `COUNTER_OFFER` | все F; предложение не означает принятие или выдачу |
| `stop_factor_share` | заявки с решением F и хотя бы одним `STOP_FACTOR_TRIGGERED` | число F; код не требует, чтобы исход был `DECLINED`, и не дает разбивки по причинам |
| `override_share` | все ручные `DECISION_MADE` с итоговым исходом и `override = true` по C | все ручные `DECISION_MADE` с итоговым исходом по C, включая повторные |
| `integration_failed_attempt_share` | все `SOURCE_REQUEST_FAILED` по C | эти ошибки плюс `SOURCE_REQUEST_SUCCEEDED` с `from_cache = false`; успешные ответы из кеша исключены, повторы считаются отдельными попытками |
| `enrichment_retries` | события `ENRICHMENT_RETRY_SCHEDULED` по C | абсолютное число повторов |
| `processing_error_applications` | заявки C с хотя бы одним `PROCESSING_FAILED` | абсолютное число, даже если позже обработка восстановлена |
| `status_now` | число заявок C по последнему `STATUS_CHANGED.to_status` | абсолютные числа на конец доступного наблюдения; без такого события статус `null` |

SLA очереди задается `manual_review_sla_hours = 8`, но `compute_metrics` не пересчитывает этот срок: он проверяет наличие события нарушения. Даже позднее нарушение повторного рассмотрения исключает заявку из числителя. Время ожидания `REVIEW_TAKEN.wait_sec` и разбивка отказов или ошибок по источникам в `build_report` не рассчитываются.

## 5. Качество скоринга и границы бизнес-выводов

Метрики `model.metrics` относятся к отдельной синтетической популяции, а не к исторической воронке: train 4 771, test 2 045, OOT 3 358 наблюдений после исключения стоп-факторов. Разработка относится к 2024H2, OOT к 2025H1. `default = 1` задан генератором, больший score означает меньший риск.

- **ROC-AUC** рассчитывается по `-score`, положительный класс `default = 1`; равные баллы учитываются как ties. **Gini = 2 * AUC - 1**.
- **KS = max по порогам s |F_bad(s) - F_good(s)|**, где `F_bad` и `F_good` являются долями наблюдений с `score <= s` внутри соответствующего класса. Знаменатели: все дефолты и все недефолты данной выборки отдельно. Группа равных баллов входит в порог целиком. KS не зависит от перестановки строк, при одинаковых баллах KS = 0. Эталон использует `roc_curve(y, -score, drop_intermediate=False)`.
- **Brier = mean((pd_model - default)^2)** по всей соответствующей выборке. Здесь используется вероятность логистической модели из балла, а не табличная `pd_by_grade`.
- **PSI = sum((actual_share - expected_share) * ln(actual_share / expected_share))** по категориям. В `src.model.psi` каждая доля ограничивается снизу `0.0001`, после этого повторной нормализации нет. `model.psi` сравнивает OOT с объединенными train и test: для балла берутся децили разработки, для факторов их бины, для грейдов A-E.
- **PSI истории** `history.psi_grade_dev_vs_history = 0.0195538346` сравнивает грейды всех записей полного файла истории с ненулевым грейдом с объединенными train и test. Он не использует когорту окна 30 или 90 дней и не сравнивает эти окна между собой. В сборке берутся неокругленные доли разработки; `monitoring.grade_distribution_dev` в конфиге хранит округленный эталон для потребителей. Пороги 0,10 и 0,25 являются диагностическими ориентирами.

| Выборка | AUC | Gini | KS после учета ties |
|---|---|---|---|
| train | 0,789434 | 0,578867 | 0,418097 |
| test | 0,770649 | 0,541298 | 0,406770 |
| OOT | 0,775803 | 0,551606 | 0,451259 |

Эти значения проверяют методику на заданных генератором связях. Они не являются оценкой реальных дефолтов, экономического эффекта или прибыли банка. `pd_by_grade` откалибрована на объединенных test и OOT, поэтому OOT не является независимой проверкой этой табличной PD. Подробности и ограничения: [scoring-model.md](scoring-model.md).

Распределение грейдов выданных кредитов и ожидаемые потери `sum(PD * LGD * EAD)` отсутствуют в `compute_metrics` и `build_report`. Такой расчет потребовал бы согласованных определений экспозиции, LGD, зрелых кредитных когорт и подтвержденной PD. Прежние LGD 0,6 / 0,4 были допущениями. Даже расчет ожидаемых потерь не равен прибыли: для нее нужны доходы, стоимость фондирования, операционные затраты и фактические потери. Событие `LOAN_ISSUED` показывает выдачу, а не последующее погашение или дефолт.
