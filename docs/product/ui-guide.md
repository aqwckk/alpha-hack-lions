# Веб-интерфейс: карта экранов и UX-решения

Карта реализации не подтверждает соблюдение каждого UX-критерия во всех состояниях. Полный браузерный путь и а11y не верифицированы: [границы проверки](implementation-status.md#границы-верификации).

Статус: **реализовано в `web/`** (React 18, TypeScript, Mantine). Экраны соответствуют [screens.md](screens.md), тексты статусов и причин приходят из API ([../api/README.md](../api/README.md), раздел 5), поэтому клиент никогда не видит внутренний статус, балл, грейд и пороги. Как собрать и запустить: [../../web/README.md](../../web/README.md). Скриншоты: [../screenshots/](../screenshots/).

## 2. Какие гипотезы о болях адресует интерфейс (эффект не измерен)

| Боль ([../research/08-recommendations-for-mvp.md](../research/08-recommendations-for-mvp.md)) | Решение в интерфейсе |
|---|---|
| ПР-1: не понимаю, какой продукт и сколько платить | подбор начинается с задачи бизнеса, а не с названий продуктов; на каждой карточке платеж в месяц крупно, переплата и "что понадобится"; калькулятор прямо на карточке; подсказки к терминам открываются по нажатию и с клавиатуры |
| ПР-2: ввожу то, что банк может узнать сам | ИНН проверяется локально, сведения о компании подставляются из реестров за 1-3 секунды и показаны только для чтения с источником; анкета из нескольких понятных показателей |
| ПР-3: не знаю, что с заявкой | на каждом экране заявки три элемента: где я (прогресс из 8 шагов), что происходит, что дальше и до какой даты; статус обновляется сам; "От вас ничего не нужно" там, где клиент только ждет; уведомления только в кабинете |
| ПР-4: дозапросы размытые и по частям | все уточнения одним экраном, у каждого пункта объяснение "зачем" и подходящее поле ответа; андеррайтер видит, как клиент увидит запрос, до отправки |
| ПР-5: урезали или отказали без объяснения | контрпредложение показывается рядом с исходным запросом, отличие каждого варианта выделено ("на 1 050 000 руб. меньше", "на 1 мес. дольше"), рекомендуемый вариант помечен; отказ объясняет каждую причину и следующий шаг с датой, без раскрытия порогов |
| ПР-6: трачу время на заявку без шансов | ранняя проверка в подборе (карточка недоступна до даты) и на шаге компании (желтое предупреждение), отправить все равно можно |
| ПР-7: андеррайтер собирает данные по системам | одна карточка: расхождения, рекомендация политики, скоринг с вкладом факторов, путь правил, ответы источников с попытками, анкета, документы, дозапросы, история и комментарии |
| ПР-8: политика меняется через релиз | версии скоринговой карты и политики видны в каждом решении и на отдельном экране с параметрами |
| ПР-9: типовые заявки ждут человека | автоматическое решение приходит клиенту за секунды; в очередь попадают только заявки с причинами, причины видны в строке очереди |

## 3. Принципы интерфейса (полная проверка не выполнена)

1. **Одно следующее действие.** Главная кнопка экрана следует из клиентского статуса и `available_actions`; если действия нет, кнопки нет.
2. **Числа и даты по-человечески.** `1 200 000 ₽`, `22%`, "24 месяца", "до 30 октября, 01:59" (время по Москве).
3. **Ошибки понятные и рядом с местом.** Поле с ошибкой подсвечивается текстом сервера; сводка ошибок отправки ведет на нужный шаг; конфликт версии объясняется ("Заявка изменилась, мы обновили данные"); нет связи: баннер и автоматический повтор.
4. **Без потери данных.** Черновик сохраняется сам, индикатор "Сохранено в ..." виден на каждом шаге, повторный клик не создает второй команды.
5. **Доступность.** Семантические заголовки и списки, подписи у всех полей, фокус на заголовке после перехода, видимый фокус, ссылка "Перейти к содержимому", статус иконкой и текстом, таблицы с заголовками, графики с текстовой версией, модальные окна с ловушкой фокуса и безопасной кнопкой по умолчанию, `aria-live` для смены статуса.
6. **Телефон.** Верстка от 360 px без горизонтальной прокрутки страницы: прогресс становится вертикальным, очередь превращается в карточки, меню прячется в выдвижную панель.
7. **Честность прототипа.** Нейтральное название "Кредитный кабинет", пометка "прототип" и подпись о синтетических данных; код подписания показывается в интерфейсе с пояснением, что в реальном продукте используется электронная подпись.

## 4. Демо-режим

Когда бэкенд запущен с `DEMO_MODE=true` (`GET /api/v1/meta`), интерфейс добавляет: таблицу тестовых учетных записей на входе, свернутую "Демо-подсказку" со значениями сценария для текущего клиента (ИНН, сумма, выручка, ожидаемый итог) и демо-панель симулятора для сотрудников. В обычном режиме этих элементов нет.
